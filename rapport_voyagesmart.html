Résumé

Le projet VoyageSmart répond à une problématique majeure de l'industrie touristique contemporaine : la fragmentation de la planification de voyage. Aujourd'hui, un voyageur doit naviguer sur de multiples sites web pour comparer et réserver des vols, des nuitées d'hôtel, des séjours en villas privées, tout en essayant de construire un itinéraire cohérent. Pour pallier cette difficulté, nous avons conçu et réalisé VoyageSmart, une plateforme web centralisée et intelligente.

L'application s'articule autour d'une architecture découplée (découple Frontend-Backend) reposant sur un frontend dynamique en React 19 (Vite) avec Tailwind CSS, et un backend robuste basé sur le framework Laravel 11 exposant une API REST sécurisée. La persistance des données est assurée par un système de gestion de base de données relationnelle MySQL. VoyageSmart intègre des fonctionnalités avancées telles que l'authentification sécurisée avec Laravel Sanctum, la recherche multicritère de vols et d'hébergements, l'optimisation des requêtes de favoris avec mise à jour d'interface en temps réel (Optimistic UI), et un planificateur d'itinéraire complet. Le projet a été conçu selon la méthodologie Agile (Scrum) et préparé pour un déploiement continu en production sur la plateforme Cloud Railway.

Mots-clés : Tourisme Intelligent, Planification de Voyage, API REST, Laravel 11, React 19, MySQL, Optimistic UI, Railway.

Abstract

The VoyageSmart project addresses a major challenge in the contemporary tourism industry: the fragmentation of travel planning. Today, a traveler has to navigate multiple websites to compare and book flights, hotel nights, and private stays, while trying to build a coherent itinerary. To solve this problem, we designed and built VoyageSmart, a centralized and intelligent web platform.

The application is built on a decoupled architecture consisting of a dynamic frontend using React 19 (Vite) and Tailwind CSS, and a robust backend powered by the Laravel 11 framework exposing a secured REST API. Data persistence is managed by a MySQL relational database management system. VoyageSmart features advanced functionalities such as secure authentication using Laravel Sanctum, multi-criteria flight and accommodation searches, optimized favorite-toggling actions utilizing real-time interface updates (Optimistic UI), and a comprehensive journey planner. The project was developed following the Agile (Scrum) methodology and prepared for continuous production deployment on the Railway cloud platform.

Keywords : Smart Tourism, Travel Planning, REST API, Laravel 11, React 19, MySQL, Optimistic UI, Railway.

Introduction Générale

Dans un monde globalisé et fortement numérisé, le secteur du tourisme et des loisirs a connu des transformations majeures. Le comportement des consommateurs a évolué vers plus d'autonomie : les voyageurs préparent désormais eux-mêmes leurs séjours sur internet. Cependant, cette liberté s'accompagne d'une complexité accrue. En effet, l'organisation d'un voyage complet (incluant la réservation d'un vol aller-retour, d'hébergements de type hôtel traditionnel ou villa privée, et la planification d'un itinéraire quotidien) reste une expérience fragmentée. Un utilisateur doit généralement naviguer sur de multiples sites et applications, multiplier les comptes clients et faire face à des interfaces hétérogènes.

Cette fragmentation entraîne une perte de temps conséquente, des risques d'erreurs dans la coordination des dates de réservations et une charge cognitive élevée pour les voyageurs. Face à ce constat, l'émergence de plateformes centralisées de type "tout-en-un" devient une nécessité évidente pour simplifier l'expérience client.

Le présent projet de synthèse s'inscrit dans ce cadre à travers la conception et la réalisation de VoyageSmart, une application web complète visant à centraliser et fluidifier la planification et la réservation de voyages. En combinant la robustesse du framework backend Laravel 11 et la réactivité du framework frontend React 19, VoyageSmart permet d'agréger la recherche de vols, la location de villas privées (Stays), la réservation de chambres d'hôtels de luxe (Hotels), la création d'itinéraires intelligents (Plans) et la gestion de favoris.

Ce rapport présente le processus complet de développement du projet VoyageSmart. Le premier chapitre définit le cadrage du projet, détaillant le contexte, la problématique, les objectifs et la méthodologie Scrum adoptée. Le deuxième chapitre effectue une étude préliminaire des solutions du marché et présente l'environnement technologique retenu. Le troisième chapitre aborde l'analyse fonctionnelle et conceptuelle du système à l'aide de diagrammes UML (cas d'utilisation, séquence, classes) et de la modélisation de la base de données. Enfin, le quatrième chapitre décrit la réalisation technique, l'architecture du code, les snippets clés et le processus de déploiement en production sur Railway.

Chapitre 1 – Cadrage du projet

Introduction du chapitre : Ce chapitre introduit le cadre méthodologique et stratégique du projet VoyageSmart. Il précise le contexte global, définit les objectifs stratégiques de la plateforme, modélise les besoins fonctionnels et techniques, et détaille le mode d'organisation de type Agile/Scrum ayant guidé le projet.

1.1 Contexte et problématique

L'organisation moderne d'un voyage à l'ère du numérique repose sur la consultation frénétique d'une multitude d'outils. Un voyageur type commence par chercher un vol adapté sur un comparateur de vols (Skyscanner, Google Flights), réserve ensuite un hôtel sur une autre plateforme (Booking.com, Hotels.com) ou cherche un hébergement alternatif chez l'habitant (Airbnb). Ensuite, pour organiser son itinéraire journalier, il utilise des blogs, des guides ou des outils de cartographie.

Cette dispersion de l'information pose plusieurs problèmes fondamentaux :

  • Le manque de synchronisation : Si un vol est modifié ou annulé, le voyageur doit manuellement modifier ses réservations d'hôtels sur une autre plateforme, augmentant les risques de pénalités financières.
  • Une expérience utilisateur décousue : Passer d'une interface à l'autre altère le confort visuel et fonctionnel.
  • Une perte de données : Il est difficile d'avoir une vision globale et consolidée de son voyage sans créer soi-même des feuilles de calcul manuelles.

VoyageSmart intervient à ce niveau précis en proposant un écosystème centralisé qui rassemble toutes ces briques logicielles au sein d'une seule interface moderne, fluide et uniforme.

1.2 Objectifs du projet

L'objectif principal du projet VoyageSmart est de fournir une plateforme Web unifiée et performante permettant de :

  1. Centraliser les recherches et les réservations : Permettre de chercher des vols, des nuitées d'hôtels et des séjours de vacances sur la même plateforme.
  2. Faciliter la planification (Smart Planning) : Proposer un outil de création d'itinéraires (Plans) où le voyageur peut lier de manière cohérente ses réservations de transports et d'hébergements.
  3. Garantir une expérience interactive fluide : Implémenter des mécanismes modernes de retour utilisateur rapide (comme l'ajout instantané en favoris par Optimistic UI) et une navigation dynamique sans rechargement.
  4. Assurer l'administration simplifiée : Fournir une console d'administration sécurisée permettant aux gestionnaires de mettre à jour le catalogue de services (vols, hôtels, séjours) et de suivre les réservations clients.

1.3 Besoins fonctionnels et non fonctionnels

1.3.1 Besoins Fonctionnels

Les exigences fonctionnelles décrivent les actions concrètes que le système doit être capable d'exécuter. Nous les avons structurées par rôle utilisateur :

A. Espace Visiteur (Non authentifié)

  • Recherche et consultation : Rechercher et consulter les hébergements (hôtels et séjours en villas) et les vols disponibles sans obligation de connexion.
  • Inscription et connexion : Créer un compte client ou s'authentifier de manière sécurisée.
  • Simulation de disponibilité : Simuler les réservations en saisissant des dates pour vérifier en temps réel la disponibilité.

B. Espace Client Voyageur (Authentifié)

  • Gestion du profil : Consulter ses informations personnelles.
  • Processus de réservation : Réserver des vols, des séjours ou des chambres d'hôtel avec attribution de numéros de chambres ou de sièges.
  • Gestion des favoris : Marquer un hôtel, un vol ou un séjour comme favori avec un affichage réactif et interactif.
  • Création d'itinéraires (Plans) : Créer, modifier et structurer un plan de voyage personnalisé associant des vols et hébergements réservés.
  • Suivi et annulation : Visualiser l'historique de ses réservations actives et passées, avec option d'annulation.

C. Espace Administrateur

  • Gestion du catalogue : Ajouter, modifier ou supprimer des vols (compagnie, origine, destination, dates, prix) et des hébergements (villas, hôtels).
  • Suivi des réservations globales : Superviser l'ensemble des réservations passées sur la plateforme.
  • Gestion des utilisateurs : Consulter la liste des comptes enregistrés sur la plateforme.

1.3.2 Besoins Non Fonctionnels

Les besoins non fonctionnels définissent les contraintes de qualité et d'implémentation du système :

  • Performance et réactivité : Les pages et les données doivent se charger en moins de 2 secondes. L'interaction utilisateur (comme l'ajout aux favoris) doit être immédiate.
  • Sécurité des données : Les mots de passe des utilisateurs doivent être chiffrés en base de données. Les requêtes de modification vers le backend doivent être filtrées par des jetons d'authentification (tokens d'accès) et protéger contre les attaques CSRF.
  • Ergonomie et responsive design : L'interface doit être totalement compatible avec les formats mobiles, tablettes et ordinateurs.
  • Scalabilité et déploiement continu : Le projet doit être configuré pour être facilement hébergé sur des infrastructures Cloud modernes (Railway) avec prise en charge automatique des builds et variables d'environnement.

1.4 Méthodologie adoptée (Agile / SCRUM)

Pour mener à bien le développement de VoyageSmart en respectant les délais et en garantissant une adaptabilité maximale face aux imprévus, nous avons adopté la méthodologie agile Scrum.

Cette méthodologie repose sur les rôles et rituels suivants :

  • Product Owner (PO) : Définit la vision du projet et ordonne le Product Backlog.
  • Scrum Master : S'assure du respect des rituels Scrum et élimine les obstacles techniques.
  • Sprint Planning : Séance de planification au début de chaque cycle de 2 semaines (Sprint) pour définir l'objectif du sprint.
  • Sprint Review & Retrospective : Évaluation de l'incrément logiciel produit à la fin de chaque sprint et identification des axes d'amélioration.

Chapitre 2 – Étude préliminaire et technologies

Introduction du chapitre : Ce chapitre dresse un état de l'art du e-tourisme en analysant les plateformes existantes. Il justifie ensuite les choix technologiques pour le Frontend, le Backend et la Base de Données, et présente les outils collaboratifs utilisés par l'équipe projet.

2.1 Étude des solutions existantes et similaires

Pour positionner au mieux VoyageSmart, nous avons analysé les trois leaders mondiaux du secteur du voyage en ligne :

1. Booking.com

  • Avantages : Catalogue d'hôtels et de vols extrêmement vaste, filtres de recherche performants.
  • Limites : L'expérience reste cloisonnée. Il est complexe d'associer un vol et un hôtel de manière chronologique dans un itinéraire unifié et interactif. De plus, l'interface utilisateur est surchargée d'informations commerciales.

2. Airbnb

  • Avantages : Excellente expérience pour les hébergements originaux (Stays), interface épurée et moderne.
  • Limites : N'intègre pas la réservation de vols. Ne propose pas d'outil de planification de voyage à étapes pour organiser un long circuit.

3. Skyscanner

  • Avantages : Comparateur de vols performant.
  • Limites : Redirige l'utilisateur vers des sites tiers pour finaliser les réservations, augmentant la fragmentation de l'expérience d'achat.

Positionnement de VoyageSmart : VoyageSmart se positionne au croisement de ces solutions. Elle combine la recherche d'hébergements de type Airbnb, la rigueur de réservation de chambres d'hôtels de type Booking, la simplicité de sélection de vols et y ajoute une valeur unique : un générateur d'itinéraires (Smart Plans) qui unifie le tout de manière chronologique.

2.2 Présentation des technologies et frameworks retenus

2.2.1 Frontend : React 19

Le choix de React 19 (utilisant l'environnement de build rapide Vite) se justifie par plusieurs atouts techniques :

  • Single Page Application (SPA) : Permet de naviguer entre la recherche, les réservations et le profil sans rechargement de page, offrant une fluidité proche d'une application mobile native.
  • Composants réutilisables : Les cartes d'hôtels, de vols, les boutons de favoris ou de formulaires de dates sont développés comme des briques réutilisables.
  • Performance du DOM Virtuel : Optimise la vitesse de mise à jour des éléments complexes de l'interface (comme la réorganisation dynamique des listes filtrées).
  • Tailwind CSS : Framework CSS utilitaire permettant de concevoir un design haut de gamme, moderne et adaptatif rapidement.

2.2.2 Backend : Laravel 11

Pour le développement de l'API, nous avons choisi Laravel 11, la dernière version majeure du framework PHP. Ses avantages sont :

  • Eloquent ORM : Facilite la communication avec la base MySQL via des modèles orientés objet élégants, évitant l'écriture de requêtes SQL brutes complexes.
  • Laravel Sanctum : Système de génération de jetons d'accès (API Tokens) léger et sécurisé pour l'authentification sans session d'état (Stateless JWT-like).
  • Architecture MVC clean : Séparation claire entre les modèles de données, le traitement métier (Contrôleurs) et l'accès réseau (Routes).
  • Prise en charge native de la production : Gestion aisée de la configuration via `.env`, outils de migration robustes, cache performant pour les routes et la configuration.

2.2.3 Base de données : MySQL

Puisque notre modèle de données implique de fortes relations d'intégrité (les réservations appartiennent à des utilisateurs et pointent sur des vols/hébergements précis), une base relationnelle est indispensable. MySQL a été sélectionné pour sa robustesse, sa compatibilité native avec Laravel et sa facilité d'hébergement.

2.3 Outils de développement et de collaboration

  • VS Code : Éditeur de code principal, enrichi d'extensions d'analyse syntaxique (ESLint, PHP Intelephense).
  • Postman : Outil utilisé tout au long du projet pour tester, documenter et valider les routes d'API Laravel avant leur intégration dans le frontend React.
  • Git & GitHub : Gestionnaire de version décentralisé permettant le versioning du code et la collaboration à l'aide de branches fonctionnelles.
  • Railway : Plateforme Cloud (PaaS) utilisée pour le déploiement continu. Elle s'interface directement avec GitHub pour compiler et mettre en ligne automatiquement le frontend (Vite) et le backend (Laravel via Nixpacks).

Conclusion du chapitre : Le choix d'une architecture découplée React/Laravel couplée à une base MySQL constitue un socle technologique moderne, évolutif et sécurisé. Le chapitre suivant détaille l'analyse fonctionnelle et la conception structurelle du projet.

Introduction du chapitre : Ce chapitre se concentre sur l'étape de modélisation du projet VoyageSmart. Il identifie les acteurs clés, formalise les cas d'utilisation, détaille les processus métier via des diagrammes de séquence, et présente la structure de la base de données (diagramme de classes et MPD).

3.1 Identification des acteurs et leurs rôles

Le système VoyageSmart interagit avec trois catégories d'acteurs :

  1. Le Visiteur : Toute personne accédant à l'application sans s'authentifier. Il peut uniquement consulter le catalogue de vols et d'hébergements et lancer des recherches.
  2. Le Client Voyageur : Utilisateur authentifié. Il hérite des droits du visiteur et peut en plus réserver des vols et hôtels, ajouter des favoris et construire ses itinéraires personnalisés (Plans).
  3. L'Administrateur : Utilisateur doté de privilèges d'administration. Il gère l'ensemble du catalogue et peut modifier les données des utilisateurs et des réservations.

4.2 Architecture générale de l'application

VoyageSmart adopte une architecture moderne découplée. Le Frontend et le Backend sont logés dans deux répertoires distincts au sein du même dépôt (Monorepo) :

  • Le dossier /backend héberge l'application Laravel, qui fait office de serveur d'API stateless.
  • Le dossier /frontend contient l'application React construite avec Vite.

La communication entre le Frontend et le Backend s'effectue exclusivement par des requêtes HTTP asynchrones au format JSON, gérées par le client Axios. L'authentification est sécurisée par le middleware Laravel Sanctum qui associe un token d'accès (Bearer Token) à chaque requête protégée.

4.3.2 Implémentation du Contrôleur de Favoris

Le FavoriteController gère l'ajout et le retrait d'éléments en favoris via une action unique de "bascule" (toggle), optimisant le code côté serveur : 

namespace App\Http\Controllers;

use Illuminate\Http\Request;
use App\Models\Favorite;
use Illuminate\Support\Facades\Auth;

class FavoriteController extends Controller
{
    public function index()
    {
        $userId = Auth::id();
        return response()->json(Favorite::where('user_id', $userId)->get(), 200);
    }

    public function toggle(Request $request)
    {
        $request->validate([
            'item_type' => 'required|string',
            'item_id' => 'required|integer'
        ]);

        $userId = Auth::id();
        $itemType = $request->item_type;
        $itemId = $request->item_id;

        $existing = Favorite::where('user_id', $userId)
                            ->where('item_type', $itemType)
                            ->where('item_id', $itemId)
                            ->first();

        if ($existing) {
            $existing->delete();
            return response()->json(['status' => 'removed'], 200);
        }

        Favorite::create([
            'user_id' => $userId,
            'item_type' => $itemType,
            'item_id' => $itemId
        ]);

        return response()->json(['status' => 'added'], 201);
    }
}

4.4 Implémentation du frontend (React)

4.4.1 Configuration Axios avec Intercepteur

Pour éviter de réécrire manuellement l'en-tête d'authentification à chaque appel d'API, nous avons configuré une instance Axios globale dans frontend/src/api/axios.js : 

import axios from 'axios';

export const BACKEND_URL = import.meta.env.VITE_API_URL || 'http://localhost:8000';

const api = axios.create({
    baseURL: `${BACKEND_URL}/api`,
    headers: {
        'Content-Type': 'application/json',
        'Accept': 'application/json',
    },
});

// Intercepteur pour injecter automatiquement le Token JWT/Sanctum
api.interceptors.request.use(
    (config) => {
        const token = localStorage.getItem('token');
        if (token) {
            config.headers.Authorization = `Bearer ${token}`;
        }
        return config;
    },
    (error) => {
        return Promise.reject(error);
    }
);

export default api;

4.4.2 Optimisation UI : Favoris avec "Optimistic UI Updates"

Pour éviter le délai visuel d'une demi-seconde lors d'un clic sur le bouton de favori, nous avons implémenté la logique Optimistic UI dans FavoriteButton.jsx. L'état visuel bascule immédiatement à l'écran, et la requête réseau est exécutée en tâche de fond. Si elle échoue, l'état visuel est annulé : 

const handleToggle = async (e) => {
  e.preventDefault();
  e.stopPropagation();

  const token = localStorage.getItem('token');
  if (!token) {
    alert('Please log in to save to favorites.');
    return;
  }

  // Sauvegarde de l'état actuel et changement immédiat (Optimiste)
  const previousState = isFavorite;
  const expectedState = !isFavorite;
  setIsFavorite(expectedState);
  if (onToggle) onToggle(expectedState);

  try {
    const response = await api.post('/favorites/toggle', {
      item_type: itemType,
      item_id: itemId
    });

    if (response.status === 200 || response.status === 201) {
      const actualValue = response.data.status === 'added';
      // Ajustement au cas improbable où le serveur retourne un état différent
      if (actualValue !== expectedState) {
        setIsFavorite(actualValue);
        if (onToggle) onToggle(actualValue);
      }
    }
  } catch (error) {
    console.error("Error toggling favorite:", error);
    // Annulation en cas d'erreur réseau
    setIsFavorite(previousState);
    if (onToggle) onToggle(previousState);
  }
};

4.6 Difficultés rencontrées et solutions apportées

1. Déploiement d'un Monorepo sur Railway

Difficulté : Par défaut, les plateformes PaaS comme Railway s'attendent à trouver un unique projet à la racine du dépôt Git. La présence simultanée du dossier `/backend` et `/frontend` empêchait le processus de build automatique de détecter le type d'application (PHP/Node).

Solution : Nous avons séparé le déploiement sur Railway en créant deux services Cloud distincts à partir du même dépôt GitHub. Pour le service backend, nous avons défini le paramètre Root Directory sur /backend. Pour le service frontend, nous l'avons configuré sur /frontend. Les builds ont ainsi été isolés avec succès.

2. Configuration des CORS en production

Difficulté : Le navigateur du client bloquait les requêtes du frontend (ex: `https://votre-frontend.up.railway.app`) vers le backend (ex: `https://votre-backend.up.railway.app`) en raison des règles de sécurité de partage de ressources d'origines différentes (CORS).

Solution : Nous avons ajusté les fichiers d'environnement pour définir la variable FRONTEND_URL côté Laravel, et configurer la politique de CORS pour autoriser de manière stricte et dynamique le domaine généré par le frontend sur Railway.

3. Démarrage de l'application React statique (Vite)

Difficulté : En production, l'application React compilée génère des fichiers HTML/JS statiques dans le dossier `/dist`. Il n'y a pas de serveur Node natif pour les servir, provoquant des erreurs 404 sur les routes gérées par le routeur React (`react-router-dom`).

Solution : Nous avons ajouté la dépendance légère serve dans le fichier package.json du frontend et modifié le script de démarrage en production : "start": "npx serve -s dist -l ${PORT:-3000}". Le flag -s (single-page-app) force toutes les requêtes à être redirigées vers `index.html`, permettant à React Router de gérer les routes internes sans plantage.
